**Версия:** 3.1 (Flat List / State Machine / Polygons / Hardware Config)  
**Область применения:** Компиляторы/декомпиляторы ГИС-данных для носимых устройств платформы C175C1 (DT NO.1 G1)

## 1. ГЛОБАЛЬНЫЙ ЗАГЛОВОК СЛОЯ (YZL HEADER)

Каждый бинарный файл картографического слоя (`.idx`, `.mlp`, `.db`) обязан начинаться с глобального системного заголовка фиксированной длины **32 байта**. Заголовок используется загрузчиком прошивки для маппинга памяти, проверки целостности (MD5).

### Таблица 1.1. Побайтовая структура заголовка YZL
| Смещение | Размер | Тип данных | Описание поля | Значение / Формат |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 3 | `char[3]` | Магическая сигнатура (Magic) | Строго `b'YZL'` (`59 5A 4C`) |
| `0x03` | 1 | `uint8` | **Функция не ясна** |Для файлов .idx принимает значения 0x0C, для .mlp и .db равен 0x00 |
| `0x04` | 4 | `uint32` | **Размер полезной нагрузки (Payload Size)** в байтах (Little-Endian). Формула: `Размер файла - 32`. | Зависит от объема данных 
| `0x08` | 4 | `uint32` | **Функция не ясна** | b'\x00\x00\x00\x04' - (Big-Endian, 4 байта), также в заводских файлах бывает значение b'\x01\x00\x00\x04 |
| `0x0C` | 4 | `uint32` | **Размер секции LOD 2 в байтах** (Big-Endian). Используется графическим движком для быстрого аппаратного прыжка (fseek) с конца файла для вычисления указателя начала LOD 2 при максимальном отдалении карты. Для файлов .mlp и .db всегда 0x00000000. | Переменное (напр., 0x00 00 00 D4) |
| `0x10` | 16 | `byte[16]`| **Контрольная сумма MD5**. Вычисляется аппаратно. Хэш берется строго от всего тела полезной нагрузки (смещение `0x20` и до конца файла). | Переменное (стандартный MD5) |

## 2. СТРУКТУРА ФАЙЛА ГЕОМЕТРИИ (.MLP)

Файл `.mlp` содержит сырые упорядоченные координаты вершин линейных и полигональных объектов (unified polyline/polygon storage). Координаты представлены в целочисленном формате фиксированной точности.

### 2.1. Локальный заголовок геометрии (Geometry Record Header)
Сразу после 32 байт глобального заголовка YZL начинается массив записей геометрии. Каждая запись предваряется собственным 8-байтовым мини-заголовком.

| Смещение | Размер | Тип данных | Эндианность | Описание поля |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 4 | `uint32` | **Big-Endian** (`>I`) | Порядковый номер геометрической записи (начиная с 1) |
| `0x04` | 4 | `uint32` | **Little-Endian** (`<I`) | Длина тела геометрической записи в байтах (Content Length) |

### 2.2. Тело геометрической записи (Geometry Record Body)
Размер тела записи в байтах строго равен значению поля `Content Length`.

| Смещение в теле | Размер | Тип данных | Описание поля / Специфика |
| :--- | :--- | :--- | :--- |
| `0x00` |16 | int32[4] | bbox_int = [minx,miny,maxx,maxy]|
| `0x10` | 4 | `int32` | `num_parts` — суммарное количество сегментов/колец в объекте |
| `0x14` | 4 | `int32` | `num_points` — суммарное количество точек (вершин) в объекте |
| `0x18` | `num_parts * 4` | `uint32[]` | Массив `parts`. Хранит индексы (смещения) точек, с которых начинается каждый сегмент (начиная с 0). Это именно индексы, а не длины контуров. |
| `0x18 + (num_parts * 4)`| `num_points * 8` | `int32[2][]` |Массив points. Массив пар целых чисел [X, Y]. Формула перевода: Координата (Float) = Значение (Int) / 1 000 000.0|



### 2.3. Топология полигонов (Мультиполигоны)
Аппаратный триангулятор поддерживает структуру сложных полигонов (например, озер с островами), аналогичную формату ESRI Shapefile:
* Все точки всех колец (как внешних контуров, так и внутренних "дырок") сплющиваются в единый массив `points`.
* Поле `num_parts` указывает общее количество колец в мультиполигоне.
* Массив `parts` (идущий перед `points`) содержит индексы начала каждого кольца (например, `[0, 41]`).
* **Winding Rules (Правило обхода):** Векторы внешнего кольца (outer) обязаны быть закручены по часовой стрелке (Clockwise). Векторы внутренних пустот (inner) должны быть закручены строго против часовой стрелки (Counter-Clockwise).
* **Outer (Внешние контуры)** — строго **По часовой стрелке (Clockwise, CW)**.
* **Inner (Внутренние дырки)** — строго **Против часовой стрелки (Counter-Clockwise, CCW)**.
* Кольца обязаны быть замкнутыми (первая и последняя координата контура должны совпадать).
Одиночные замкнутые полигоны всегда классифицируются как Outer и должны быть закручены по часовой стрелке (CW).

## 3. СТРУКТУРА ПРОСТРАНСТВЕННОГО ИНДЕКСА (.IDX)

Файл `.idx` организует данные по уровням детализации (LOD) и кластеризует их для быстрого отсечения невидимой геометрии (BBox Culling).

### 3.1. Архитектура Flat List и Аппаратный автомат состояний (State Machine)
Прошивка часов считывает индекс строго линейно с помощью аппаратного конечного автомата. Иерархические деревья не поддерживаются. Индекс состоит из 3 уровней LOD (LOD 0, LOD 1, LOD 2), каждый из которых начинается с заголовка `SQT\x01` (8 байт). Внутри LOD объекты упакованы в плоские группы (кластеры) фиксированного размера (максимум по 14 объектов данных).
Каждый кластер имеет линейную структуру из 3 последовательных фаз:
`[Узел навигации] -> [Заголовок кластера] -> [Массив из N узлов данных]`
Структура [Узел навигации] -> [Заголовок кластера] -> [Узлы данных] строго соблюдается для многокластерных уровней (LOD 0).
Аппаратная оптимизация (Omission): Если уровень детализации состоит ровно из одного кластера (что типично для обзорных уровней LOD 1 и LOD 2), Узел Навигации (Nav Node) полностью опускается. В этом случае сигнатура SQT\x01 сопровождается сразу Заголовком Кластера (v1 = 0).

Любой узел (Node) в файле `.idx` имеет фиксированный размер **28 байт**.

```text
+------------------------------------------------------------+
|                       LOD LEVEL 0                          |
+------------------------------------------------------------+
|  [SQT Header] (8 байт)                                     |
|  +------------------------------------------------------+  |
|  | КЛАСТЕР 1                                            |  |
|  |  - Навигационный узел (Navigation Node)    (28 байт) |  | --+ Указатель прыжка v3
|  |  - Заголовок кластера (Cluster Header)     (28 байт) |  |   | перепрыгивает весь
|  |  - Узел данных 1 (Data Node 1)             (28 байт) |  |   | этот блок, если BBox
|  |    ...                                               |  |   | вне экрана устройства
|  |  - Узел данных N (Data Node N, макс 14)    (28 байт) |  |   |
|  +------------------------------------------------------+  | <-+
|  +------------------------------------------------------+  |
|  | КЛАСТЕР 2...                                         |  |
|  +------------------------------------------------------+  |
|  | Терминатор уровня LOD 0 (b'\x00' * 8)                |  |
+------------------------------------------------------------+
```
*(Схема навигации кластера**)*

### 3.2. Спецификация типов узлов (размер каждого — 28 байт)

#### Тип 1: Навигационный узел (Navigation Node / Jump Node)
Служит для аппаратного пропуска (Culling) всего последующего кластера, если экран часов не пересекается с границами BBox этого кластера.
* **Структура упаковки:** `<IIIffff` (28 байт)

| Смещение | Размер | Тип данных | Имя поля | Правило заполнения / Системный смысл |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 4 | `uint32` | `v1` | **High Watermark (Верхняя граница геометрии)**. Указывает на абсолютный конец геометрии предыдущего кластера в файле .mlp. В самом первом кластере уровня LOD (Root) значение обязано быть строго 1 (0x00000001). Для всех последующих кластеров рассчитывается по формуле: v1 = (Абсолютное смещение конца последнего объекта предыдущего кластера) - 24. Используется автоматом состояний для аппаратного fseek при пропуске невидимых блоков.
| `0x04` | 4 | `uint32` | `v2` | **Счетчик кластеров LOD (Root Node Flag)** В самом первом Узле Навигации текущего уровня LOD (Root Node) это поле обязано содержать общее количество кластеров в этом уровне LOD. о всех последующих Узлах Навигации этого же LOD значение должно быть строго равно 1. Внимание: Значение строго >= 1. Если записать 0, прошивка вычислит db_index = 0 - 1 = -1 и уйдет в Soft Reset. |
| `0x08` | 4 | `uint32` | `v3` | Указатель аппаратного прыжка (Jump Size). Количество байт для перескока кластера при BBox Culling. <br>Аппаратная оптимизация (Early Exit): Автомат состояний прошивки читает не весь узел (28 байт), а останавливается после чтения MinY (20 байт).<br> Если объект вне экрана, выполняется прыжок от текущей позиции указателя (offset +20). <br> Чтобы перепрыгнуть недочитанные 8 байт узла и весь блок геометрии, добавляется константа +8.<br> Формула: v3 = (Количество узлов данных в кластере + 1) * 28 + 8 |
| `0x0C` | 16 | `float[4]` | `BBox` | Границы кластера в координатах float: `[MinX, MinY, MaxX, MaxY]`. |

#### Тип 2: Заголовок кластера (Cluster Header)
Переключает автомат состояний прошивки в режим пакетного чтения узлов данных.
* **Структура упаковки:** `<IIffffI` (28 байт)

| Смещение | Размер | Тип данных | Имя поля | Значение / Описание |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 4 | `uint32` | `v1` | **Строго `0`**. Сигнальный маркер для автомата состояний часов. |
| `0x04` | 4 | `uint32` | `v2` | Счетчик элементов: `Количество узлов данных в кластере + 1`. |
| `0x08` | 16 | `float[4]` | `BBox` | Дублирует `BBox` кластера (`[MinX, MinY, MaxX, MaxY]`). |
| `0x18` | 4 | `uint32` | `Code` | Код стиля рендеринга слоя (наследуется от первого объекта). |

#### Тип 3: Узел данных (Data Node)
Конечный элемент индекса. Хранит ссылки на физическую геометрию и атрибуты конкретного объекта.
* **Структура упаковки:** `<IIffffI` (28 байт)

| Смещение | Размер | Тип данных | Имя поля | Значение / Описание |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 4 | `uint32` | `v1` | **Смещение локального заголовка геометрии в .mlp**. v1 указывает строго на начало 8-байтового локального мини-заголовка записи. Формула абсолютного смещения адреса в файле: Абсолютное смещение = v1 + 24. |

| `0x04` | 4 | `uint32` | `v2` | **Индекс записи в атрибутивной БД `.db`.** Ссылка на строку в таблице dBase III. `1` — зарезервировано под пустую запись (безымянные дороги), `2` и далее — уникальные имена. |
| `0x08` | 16 | `float[4]` | `BBox` | Индивидуальный ограничивающий прямоугольник объекта `[MinX, MinY, MaxX, MaxY]`. |
| `0x18` | 4 | `uint32` | `Code` | Код класса объекта OSM (например, `5114` — secondary road). |

## 4. СТРУКТУРА БАЗЫ ДАННЫХ АТРИБУТОВ (.DB)

Файл `.db` хранит текстовые наименования (теги `name`) объектов. Формат представляет собой стандартную СУБД **dBase III (DBF)**, инкапсулированную в контейнер YZL.

### 4.1. Спецификация заголовка DBF (Размер: 161 байт)
Начинается со смещения `0x20` (сразу после 32 байт YZL заголовка).
* Магический байт dBase III: `0x03` (Смещение `0x20`).
* `Количество записей` (4 байта, Little-Endian): Смещение `0x24`. Количество строк рассчитывается как `Количество именованных объектов + 1`.
* `Размер заголовка БД` (2 байта, Little-Endian): Строго `161` (`0xA1 0x00`) на смещении `0x28`.
* `Размер одной записи` (2 байта, Little-Endian): Строго `145` (`0x91 0x00`) на смещении `0x2A`.

### 4.2. Маппинг полей записи (Record Fields)
Длина описания каждого поля — 32 байта. Терминатор описания полей — байт `0x0D`. Всего полей 4:
1. `osm_id` (Тип `C` / Символьный, длина 12 байт).
2. `code` (Тип `C` / Символьный, длина 4 байта).
3. `fclass` (Тип `C` / Символьный, длина 28 байт).
4. `name` (Тип `C` / Символьный, длина 100 байт).

### 4.3. Важность записи №0 (Record 0)
Первая физическая запись данных в `.db` файле (длиной 145 байт) **строго обязана быть полностью пустой** (заполнена `\x00`). 
* На нее ссылаются все безымянные объекты карты установкой указателя `v2 = 1`.
* Реальные именованные записи упаковываются следом и получают индексы `v2 = 2`, `v2 = 3` и т.д. Каждая запись начинается с байта `0x20` (индикатор валидности записи dBase).

## 5. АЛГОРИТМЫ ОПЕРАЦИЙ (ПСЕВДОКОД)

### 5.1. Алгоритм компиляции пространственного индекса (IDX)
```text
ВХОД: Список объектов с вычисленными v1 (из MLP), v2 (из DB), BBox и Code
ВЫХОД: Бинарный файл картографического слоя .idx

1. Инициализировать пустой байтовый буфер idx_body

2. Записать сигнатуру первого LOD: idx_body.extend(b"SQT\x01" + pack("<I", 1))

3. Разбить входной список объектов на пространственные группы (Spatial Quad Tree) размером до 14 элементов.
   Кластеры не фиксированы по длине и варьируются от 1 до 14 объектов в зависимости от их пространственной плотности.
   Плоская линейная нарезка по 14 элементов снижает эффективность Early Exit Culling.

4. Для каждой группы объектов:
    А. Вычислить общий BBox группы (min/max X и Y среди всех объектов группы)
    Б. Взять v1_safe из ПЕРВОГО объекта текущей группы (служит указателем на начало геометрии кластера в .mlp для префетчинга).
    В. Вычислить v2_nav (Root Node Flag): если это первый кластер в текущем LOD, то v2_nav = общее количество кластеров в LOD. Иначе v2_nav = 1.
    Г. Вычислить jump_v3 = ((кол_во_объектов_в_группе + 1) * 28) + 8  // Смещение +8 компенсирует аппаратный Early Exit
    Д. Упаковать Навигационный узел:
       pack("<IIIffff", v1_safe, v2_nav, jump_v3, MinX, MinY, MaxX, MaxY) -> idx_body
    Е. Упаковать Заголовок кластера:
       pack("<IIffffI", 0, кол_во_объектов_в_группе + 1, MinX, MinY, MaxX, MaxY, первый_code) -> idx_body
    Ж. Для каждого объекта в группе:
       Упаковать Узел данных:
       pack("<IIffffI", obj.v1, obj.v2, obj.MinX, obj.MinY, obj.MaxX, obj.MaxY, obj.code) -> idx_body

5. Дописать терминатор уровня LOD 0 для защиты от Underflow (8 байт).
   - Если кластеры были: записать v1 и v2 последнего обработанного узла: pack("<II", last_v1, last_v2).
   - Если кластеров не было: записать безопасную пустышку (Dummy Fallback): pack("<II", 0, 1).

6. Скомпилировать аналогичным образом секции LOD 1 и LOD 2, опустив Узлы Навигации, если секция состоит из одного кластера (<=14 объектов).

7. Вычислить lod2_size: точный размер секции LOD 2 в байтах.

8. Сформировать заголовок YZL для .idx файла: 
   b"YZL\x0C" + pack("<I", len(idx_body)) + b"\x01\x00\x00\x04" + pack(">I", lod2_size) + MD5_Hash(16 байт)

9. Сохранить Заголовок YZL + idx_body в файл LAYER_NAME.idx
```

### 5.2. Аппаратный алгоритм парсинга конечным автоматом прошивки (State Machine Parsing)
```text
ВХОД: Бинарный поток файла .idx со смещения 32 (после YZL)

1. Считать 8 байт. Если это не "SQT\x01", завершить ошибкой.
2. Установить переменную data_nodes_left = 0
3. Пока не достигнут конец текущего LOD-уровня:
    А. Считать 28 байт текущего узла.
    Б. Если узел полностью состоит из нулей -> пропустить (выравнивание).
    В. Распаковать первые 8 байт как два uint32: (v1, v2)
    Г. ЕСЛИ data_nodes_left > 0:
         - Текущий узел является УЗЛОМ ДАННЫХ (Data Node).
         - Распаковать полностью как `<IIffffI`.
         - Отправить объект на рендеринг: считать геометрию из .mlp по адресу v1, 
           и считать имя из .db по индексу v2.
         - Уменьшить data_nodes_left на 1.
       ИНАЧЕ (data_nodes_left == 0):
         - ЕСЛИ v1 == 0:
             * Текущий узел является ЗАГОЛОВКОМ КЛАСТЕРА (Cluster Header).
             * Распаковать полностью как `<IIffffI`.
             * Инициализировать счетчик автомата: data_nodes_left = v2 - 1
         - ИНАЧЕ (v1 != 0):
             * Текущий узел является УЗЛОМ НАВИГАЦИИ (Navigation Node).
             * Распаковать только первые 20 байт: `<IIIff` (`v1`, `v2`, `v3`, `MinX`, `MinY`).
             * **Early Exit Check:** Проверить пересечение `MinX` / `MinY` с экраном часов.
             * ЕСЛИ пересечения НЕТ:
                 + Выполнить аппаратный fseek: сдвинуть указатель файла вперед на `v3` байт (прыжок компенсирует недочитанные 8 байт узла + размер всего кластера).
             * ЕСЛИ пересечение ЕСТЬ:
                 + Дочитать оставшиеся 8 байт (`MaxX`, `MaxY`) и выполнить финальную проверку BBox.```
*(Логика парсинга State Machine**)*

## 6. ВНУТРЕННЯЯ ТАБЛИЦА СТИЛЕЙ (LUT) И АППАРАТНЫЙ Z-CULLING

Поле `code` (uint32), хранящееся в базе данных `.db` и дублирующееся в узлах данных `.idx` (на месте `v3`), жестко привязано к внутренней (зашитой в прошивку) таблице стилей Look-Up Table (LUT) платформы C175C1.

Формат кодов соответствует стандарту **Geofabrik GIS**. Важнейшей архитектурной особенностью является **аппаратный Z-Culling** (отсечение объектов по дальности). Часы не рендерят все объекты из файла `.idx` постоянно; они скрывают линии в зависимости от текущего масштаба карты на экране, экономя такты GPU. 

**Жестко закрепленные пороги видимости (Display Scale):**
* **Масштаб 1000+ м:** Отрисовываются только крупные магистрали (Коды `5111`, `5112`, `5113`, `5114`). Большинство полигональных слоев (landuse, water) аппаратно блокируются для экономии ресурсов GPU.
* **Масштаб 500 м:** Добавляются второстепенные дороги и съезды (`5115`, группа `513x`). На этом масштабе прошивка разрешает рендеринг полигонов (водоемы, леса).
* **Масштаб 100 м:** Добавляются улицы местного значения(группа `512x`).
* **Масштаб 50 м:** Добавляются сельскохозяйственные и технические дороги (группа `514x`).
* **Масштаб 20 м (Максимальное приближение):** Становятся видны пешеходные и велосипедные дорожки, ступени (группа `515x`).

**Инженерный вывод:** Неизвестные коды или мелкие дороги на крупных масштабах физически игнорируются графическим автоматом. Для принудительного отображения объекта (например, велодорожки `5152`) на более удаленном масштабе, требуется подмена (перемаппинг) его `code` на этапе компиляции на код с меньшим порогом отсечения (например, `5141`).

## 7. МНОГОУРОВНЕВОЕ МАСШТАБИРОВАНИЕ SQT (LOD 0, LOD 1, LOD 2)

Файл `.idx` три последовательных списка пространственного индекса, разделенных сигнатурами `SQT\x01`.

* **LOD 0 (Секция 1):** Уровень максимальной детализации. Охватывает все геометрические примитивы слоя.
* **LOD 1 (Секция 2):** Средний уровень детализации.
* **LOD 2 (Секция 3):** Обзорный уровень детализации (наименьшее количество объектов).

Каждая секция LOD начинается с 8-байтового заголовка: b'SQT\x01' + struct.pack("<I", 1).
Секция завершается 8-байтовым терминатором-пустышкой (Dummy Tail), который Содержит точную копию первых 8 байт (v1 и v2) последнего обработанного узла данных в текущей секции LOD.
Использование заглушки v2 = 1 допускается как безопасный хак (System Dummy), но оригинальный компилятор сохраняет реальный индекс.
Критическое правило: Использование нулей (b'\x00' * 8) недопустимо. При попытке автомата состояний прочитать терминатор как следующий узел, нулевое значение v2 вызовет аппаратный сбой v2=0 Underflow (попытка обратиться к db_index = 0 - 1 = -1) и отправит устройство в Soft Reset.

**Связь LOD с аппаратным Culling'ом:** Для оптимизации памяти часов, компилятор должен распределять объекты по уровням LOD в соответствии с порогами Z-Culling графического процессора. В LOD 2 должны записываться только объекты с порогом видимости `1000 м`

## 8. ОБХОД ВАЛИДАЦИИ (SYSTEM DUMMIES) И КОНФИГУРАЦИЯ

### 8.1. Пустые слои (System Dummies)
Парсер часов жестко требует наличия как минимум слоя landuse.
Пустые слои взяты из заводских карт пустой области.

### 8.2. Файл конфигурации map.name
Этот файл служит точкой входа для прошивки и определяет параметры центрирования камеры.
* **Формат данных:** Строгий JSON.
* **Обязательная структура:** `{"centerLat": float, "centerLon": float, "mapName": string}`
* **Расчет координат:** Значения `centerLat` и `centerLon` высчитываются как геометрический центр глобального BBox (Bounding Box) всех скомпилированных слоев карты.
* **Критическое требование к парсингу:** Встроенный JSON-парсер часов примитивен и не переносит лишних whitespaces (пробелов). При компиляции файла конфигурации недопустимо использование форматирования (pretty-print). При использовании Python, сериализацию необходимо выполнять строго с параметром `separators=(',', ':')`, чтобы сжать JSON в единую строку.
