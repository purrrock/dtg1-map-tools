# ТЕХНИЧЕСКАЯ СПЕЦИФИКАЦИЯ ФОРМАТА КАРТ DT G1 (реверс-инжинириг)

**Версия:** 4.0 (C-Union Node / Mode Switch)
**Область применения:** Компиляторы/декомпиляторы ГИС-данных для носимых устройств платформы ATS3085S (DT NO.1 G1)

---

## 1. ГЛОБАЛЬНЫЙ ЗАГЛОВОК СЛОЯ (YZL HEADER)

Каждый бинарный файл картографического слоя (`.idx`, `.mlp`, `.db`) обязан начинаться с глобального системного заголовка фиксированной длины **32 байта**. Заголовок используется загрузчиком прошивки для маппинга памяти, проверки целостности (MD5).

### Таблица 1.1. Побайтовая структура заголовка YZL
| Смещение | Размер | Тип данных | Описание поля | Значение / Формат |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 3 | `char[3]` **| Магическая сигнатура (Magic)** | Строго `b'YZL'` (`59 5A 4C`) |
| `0x03` | 1 | `uint8` | **Расширение магии файла** |Для файлов для .mlp и .db равен 0x00, для .idx принимает различные значения (например 0x08, 0x10, 0x0C) |
| `0x04` | 4 | `uint32` | **Размер полезной нагрузки (Payload Size)** в байтах (Little-Endian). Формула: `Размер файла - 32`. | Зависит от объема данных 
| `0x08` | 4 | `uint32` | **Определяет тип загрузки в RAM.** | Для .mlp/.db = 0x00 00 00 00. Для .idx = 0x02 00 00 04 (Little-Endian: 0x04000002). |
| `0x0C` | 4 | `uint32` | **Размер секции LOD 2 в байтах** (Big-Endian). Используется графическим движком для быстрого аппаратного прыжка (fseek) с конца файла для вычисления указателя начала LOD 2 при максимальном отдалении карты. Для файлов .mlp и .db всегда 0x00000000. | Переменное (напр., 0x00 00 00 D4) |
| `0x10` | 16 | `byte[16]`| **Контрольная сумма MD5**. Вычисляется аппаратно. Хэш берется строго от всего тела полезной нагрузки (смещение `0x20` и до конца файла). | Переменное (стандартный MD5) |

**(Исключение для слоя pois.idx):**
* **Смещение `0x03` (Расширение магии):** Значение строго `0x00`.
* **Смещение `0x08` (Тип загрузки в RAM):** Принимает значение `0x00 00 00 04` (Little-Endian: `0x04000000`), идентично заголовкам `.mlp` и `.db`.

## 2. СТРУКТУРА ФАЙЛА ГЕОМЕТРИИ (.MLP)

Файл `.mlp` содержит сырые упорядоченные координаты вершин линейных и полигональных объектов (unified polyline/polygon storage). Координаты представлены в целочисленном формате фиксированной точности.

### 2.1. Локальный заголовок геометрии (Geometry Record Header)
Сразу после 32 байт глобального заголовка YZL начинается массив записей геометрии. Каждая запись предваряется собственным 8-байтовым мини-заголовком.

| Смещение | Размер | Тип данных | Эндианность | Описание поля |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 4 | `uint32` | **Big-Endian** (`>I`) | Порядковый номер геометрической записи (начиная с 1) |
| `0x04` | 4 | `uint32` | **Little-Endian** (`<I`) | Длина тела геометрической записи в байтах (Content Length) |

### 2.2. Тело геометрической записи (Geometry Record Body)
Размер тела записи в байтах строго равен значению поля `Content Length`.

| Смещение в теле | Размер | Тип данных | Описание поля / Специфика |`
| :--- | :--- | :--- | :--- |
| `0x00` |16 | `int32[4]` | `bbox_int` = [minx,miny,maxx,maxy]|
| `0x10` | 4 | `int32` | `num_parts` — суммарное количество сегментов/колец в объекте |
| `0x14` | 4 | `int32` | `num_points` — суммарное количество точек (вершин) в объекте |
| `0x18` | `num_parts * 4` | `uint32[]` | Массив `parts`. Хранит индексы (смещения) точек, с которых начинается каждый сегмент (начиная с 0). Это именно индексы, а не длины контуров. |
| `0x18 + (num_parts * 4)`| `num_points * 8` | `int32[2][]` |Массив points. Массив пар целых чисел [X, Y]. Формула перевода: Координата (Float) = Значение (Int) / 1 000 000.0|



### 2.3. Топология полигонов (Мультиполигоны)
Аппаратный триангулятор поддерживает структуру сложных полигонов (например, озер с островами), аналогичную формату ESRI Shapefile:
* Все точки всех колец (как внешних контуров, так и внутренних "дырок") сплющиваются в единый массив `points`.
* Поле `num_parts` указывает общее количество колец в мультиполигоне.
* Массив `parts` (идущий перед `points`) содержит индексы начала каждого кольца (например, `[0, 41]`).
* **Winding Rules (Правило обхода):** Векторы внешнего кольца (outer) обязаны быть закручены по часовой стрелке (Clockwise). Векторы внутренних пустот (inner) должны быть закручены строго против часовой стрелки (Counter-Clockwise).
* **Outer (Внешние контуры)** — строго **По часовой стрелке (Clockwise, CW)**.
* **Inner (Внутренние дырки)** — строго **Против часовой стрелки (Counter-Clockwise, CCW)**.
* Кольца обязаны быть замкнутыми (первая и последняя координата контура должны совпадать).
Одиночные замкнутые полигоны всегда классифицируются как Outer и должны быть закручены по часовой стрелке (CW).

## 3. СТРУКТУРА ПРОСТРАНСТВЕННОГО ИНДЕКСА (.IDX)

Файл `.idx` организует данные по уровням детализации (LOD) и кластеризует их для быстрого отсечения невидимой геометрии (BBox Culling).

### 3.1. Архитектура Flat List и Аппаратный автомат состояний (State Machine)
Внутри LOD объекты упакованы в плоские группы (кластеры) фиксированного размера (максимум по 14 объектов данных).

### 3.2. Спецификация типов узлов (размер каждого — 28 байт)
Архитектура узлов (C-Union Pattern)
Движок ATS3085S использует строго унифицированный 28-байтовый фрейм как для Навигационных узлов (Nav Node), так и для Узлов данных (Data Node).
Фундаментальное правило прошивки: последние 8 байт любого узла (смещение +20 и +24) всегда являются указателями v1 и v2. Это позволяет аппаратному парсеру перемещаться по графу памяти, не анализируя тип узла.

На C-подобном псевдокоде архитектура выглядит так:
struct UnifiedNode {
    union {
        struct { float xmin, ymin, xmax, ymax; uint32_t type; } data; // 20 bytes
        struct { uint32_t v3_jump; float xmin, ymin, xmax, ymax; } nav;  // 20 bytes
    } payload;
    uint32_t v1;  // offset 20
    uint32_t v2;  // offset 24
};

#### 1. Data Node (Узел данных)
Содержит непосредственно картографический примитив.
0x00 - 0x0F: BBox (4 float значения: xmin, ymin, xmax, ymax).
0x10 - 0x13: Type (uint32). Код класса объекта OSM (например, `5114` — secondary road)..
0x14 - 0x17: v1 (uint32). Указатель на начало геометрии объекта в файле .mlp. Указатель v1 в SQT-индексе должен пробивать заголовок объекта и указывать на саму полезную нагрузку (Payload), минуя 8 байт.
0x18 - 0x1B: v2 (uint32). Индекс записи атрибутов в файле .db.`1` — зарезервировано под пустую запись (безымянные), `2` и далее — уникальные имена. 
Формат распаковки (Python): <ffffIII

(Аномалия слоя POI):
* **Отсутствие .mlp:** Файл `pois.mlp` не существует в архитектуре.
* **Смещение `0x00 - 0x0F` (Point Injection):** 32-битные Float координаты (Lat/Lon) записываются напрямую в поля BBox. Требуется строгое дублирование: `minX == maxX` и `minY == maxY`.
* **Смещение `0x14 - 0x17` (v1):** Требуется уточнение. Возможно значения игнорируются графическим парсером при наличии маркера топологии `0x01000000`. В заводских картах возрастающие значения в пределах кластера.

#### 2. Nav Node (Навигационный узел)
Открывает кластер геометрии (записывается только в режиме Mode 0x01). За ним встык (без прокладок) следуют узлы данных этого кластера.
0x00 - 0x03: v3_jump (uint32). Указатель относительного прыжка (Early Exit) для обхода кластера, если его BBox не попадает в экран. Внимание: Требует аппаратной компенсации префетча процессора! Формула: (Количество Data Nodes * 28) + 8.
0x04 - 0x13: BBox кластера (4 float значения, охватывающих все объекты внутри).
0x14 - 0x17: v1 (uint32). Всегда аппаратный ноль (маркер Nav-типа для внутренней стейт-машины).
0x18 - 0x1B: v2 (uint32). Строго содержит количество Data Nodes, вложенных в данный кластер.
Формат распаковки (Python): <IffffII

## 4. СТРУКТУРА БАЗЫ ДАННЫХ АТРИБУТОВ (.DB)

Файл `.db` хранит текстовые наименования (теги `name`) объектов. Формат представляет собой стандартную СУБД **dBase III (DBF)**, инкапсулированную в контейнер YZL.

### 4.1. Спецификация заголовка DBF (Размер: 161 байт)
Начинается со смещения `0x20` (сразу после 32 байт YZL заголовка).
* Магический байт dBase III: `0x03` (Смещение `0x20`).
* `Количество записей` (4 байта, Little-Endian): Смещение `0x24`. Количество строк рассчитывается как `Количество именованных объектов + 1`.
* `Размер заголовка БД` (2 байта, Little-Endian): Строго `161` (`0xA1 0x00`) на смещении `0x28`.
* `Размер одной записи` (2 байта, Little-Endian): Строго `145` (`0x91 0x00`) на смещении `0x2A`.

### 4.2. Маппинг полей записи (Record Fields)
Длина описания каждого поля — 32 байта. Терминатор описания полей — байт `0x0D`. Всего полей 4:
1. `osm_id` (Тип `C` / Символьный, длина 12 байт).
2. `code` (Тип `C` / Символьный, длина 4 байта).
3. `fclass` (Тип `C` / Символьный, длина 28 байт).
4. `name` (Тип `C` / Символьный, длина 100 байт).

### 4.3. Важность записи №0 (Record 0)
Первая физическая запись данных в `.db` файле (длиной 145 байт) **строго обязана быть полностью пустой** (заполнена `\x00`). 
* На нее ссылаются все безымянные объекты карты установкой указателя `v2 = 1`.
* Реальные именованные записи упаковываются следом и получают индексы `v2 = 2`, `v2 = 3` и т.д. Каждая запись начинается с байта `0x20` (индикатор валидности записи dBase).

(Исключение для слоя POI):
* **Запрет нулевой записи:** В файле `pois.db` пустая 145-байтовая строка-заглушка отсутствует. Первая запись данных с маркером валидности `0x20` начинается сразу после терминатора заголовка `0x0D`.
* **Маппинг `v2`:** Применяется прямая адресация (1-based indexing). Указатель `v2 = 1` внутри `pois.idx` ссылается на первую физическую запись атрибутов в базе данных. Безымянные POI не заносятся в БД, а их узлы получают `v2 = 0`.

## 5. АЛГОРИТМЫ ОПЕРАЦИЙ (ПСЕВДОКОД)

### 5.1. Алгоритм компиляции пространственного индекса (IDX)
```text
ВХОД: Список объектов с вычисленными v1 (из MLP), v2 (из DB), BBox и Code
ВЫХОД: Бинарный файл картографического слоя .idx

1. Инициализировать пустой байтовый буфер idx_body

2. Записать сигнатуру первого LOD: idx_body.extend(b"SQT\x01" + pack("<I", 1))

3. Разбить входной список объектов на пространственные группы (Spatial Quad Tree) размером до 14 элементов.
   Кластеры не фиксированы по длине и варьируются от 1 до 14 объектов в зависимости от их пространственной плотности.

4. Для каждой группы объектов:
  А. Вычислить общий BBox группы (min/max X и Y среди всех объектов группы).
  Б. Вычислить nav_v1: для первого кластера = 0. Для последующих = указатель v1 на абсолютный конец геометрии предыдущего кластера.
  В. Вычислить nav_v2 = количеству объектов в текущем кластере.
  Г. Вычислить jump_v3 = (кол_во_объектов_в_группе * 28) + 8  // Смещение +8 компенсирует префетч процессора.
  Д. Упаковать Навигационный узел (Nav Node):
     pack("<IffffII", jump_v3, MinX, MinY, MaxX, MaxY, nav_v1, nav_v2) -> idx_body
  Е. Для каждого объекта в группе встык за навигационным узлом:
     Упаковать Узел данных (Data Node):
     pack("<ffffIII", obj.MinX, obj.MinY, obj.MaxX, obj.MaxY, obj.code, obj.v1, obj.v2) -> idx_body


5. Скомпилировать аналогичным образом секции LOD 1 и LOD 2, опустив Узлы Навигации, если секция состоит из одного кластера (<=14 объектов).
Никаких терминаторов и аппаратных выравниваний (padding) в индексе не существует. > Узлы всегда располагаются встык друг к другу и к заголовкам следующих секций.
Если LOD заполнен, после последнего байта последнего Data Node сразу же начинается сигнатура SQT\x01 следующего уровня.
Если LOD пуст (0 объектов), секция состоит строго из 16 байт заголовка: [SQT\x01] [00 00 00 00] [Mode = 00 00 00 00] [Count = 00 00 00 00].

6. Вычислить lod2_size: точный размер секции LOD 2 в байтах.

7. Сформировать заголовок YZL для .idx файла: 
   b"YZL\x0C" + pack("<I", len(idx_body)) + b"\x01\x00\x00\x04" + pack(">I", lod2_size) + MD5_Hash(16 байт)

8. Сохранить Заголовок YZL + idx_body в файл LAYER_NAME.idx
```

### 5.2. Аппаратный алгоритм парсинга конечным автоматом прошивки (State Machine Parsing)
```# 1. Читаем заголовок SQT (16 байт)
magic, res, mode, count = struct.unpack("<IIII", file.read(16))

if count == 0:
    return # Пустой LOD, переходим к следующему

if mode == 0x00: # Flat List Mode
    for _ in range(count):
        node_bytes = file.read(28)
        xmin, ymin, xmax, ymax, obj_type, v1, v2 = struct.unpack("<ffffIII", node_bytes)
        render_object(xmin, ymin, xmax, ymax, obj_type, v1, v2)

elif mode == 0x01: # Clustered Mode
    for _ in range(count):
        nav_bytes = file.read(28)
        v3_jump, c_xmin, c_ymin, c_xmax, c_ymax, nav_v1, obj_count = struct.unpack("<IffffII", nav_bytes)
        
        if not is_in_screen(c_xmin, c_ymin, c_xmax, c_ymax):
            # Culling: Прыгаем на следующий Nav Node
            # v3_jump УЖЕ включает +8 байт компенсации префетча аппаратного конвейера!
            # В парсере это эквивалентно: file.seek(v3_jump - 8, SEEK_CUR)
            file.seek(v3_jump - 8, 1) 
            continue
            
        # Кластер видим, читаем вложенные Data Nodes
        for _ in range(obj_count):
            data_bytes = file.read(28)
            xmin, ymin, xmax, ymax, obj_type, v1, v2 = struct.unpack("<ffffIII", data_bytes)
            render_object(xmin, ymin, xmax, ymax, obj_type, v1, v2)```

## 6. ВНУТРЕННЯЯ ТАБЛИЦА СТИЛЕЙ (LUT) И АППАРАТНЫЙ Z-CULLING

Поле `code` (uint32), хранящееся в базе данных .db и дублирующееся в узлах данных .idx (смещение 0x10, перекрывающееся с координатой ymax навигационного узла в структуре C-Union), жестко привязано к внутренней (зашитой в прошивку) таблице стилей Look-Up Table (LUT).
Формат кодов соответствует стандарту **Geofabrik GIS**. Важнейшей архитектурной особенностью является **аппаратный Z-Culling** (отсечение объектов по дальности). Часы не рендерят все объекты из файла `.idx` постоянно; они скрывают линии в зависимости от текущего масштаба карты на экране, экономя такты GPU. 

**Жестко закрепленные пороги видимости (Display Scale):**
* **Масштаб 1000+ м:** Отрисовываются только крупные магистрали (Коды `5111`, `5112`, `5113`, `5114`). Большинство полигональных слоев (landuse, water) аппаратно блокируются для экономии ресурсов GPU.
* **Масштаб 500 м:** Добавляются второстепенные дороги и съезды (`5115`, группа `513x`). На этом масштабе прошивка разрешает рендеринг полигонов (водоемы, леса).
* **Масштаб 100 м:** Добавляются улицы местного значения(группа `512x`).
* **Масштаб 50 м:** Добавляются сельскохозяйственные и технические дороги (группа `514x`).
* **Масштаб 20 м (Максимальное приближение):** Становятся видны пешеходные и велосипедные дорожки, ступени (группа `515x`).

**Инженерный вывод:** Неизвестные коды или мелкие дороги на крупных масштабах физически игнорируются графическим автоматом. Для принудительного отображения объекта (например, велодорожки `5152`) на более удаленном масштабе, требуется подмена (перемаппинг) его `code` на этапе компиляции на код с меньшим порогом отсечения (например, `5141`).

## 7. МНОГОУРОВНЕВОЕ МАСШТАБИРОВАНИЕ SQT (LOD 0, LOD 1, LOD 2)

Файл `.idx` три последовательных списка пространственного индекса, разделенных сигнатурами `SQT\x01`.

* **LOD 0 (Секция 1):** Уровень максимальной детализации. Охватывает все геометрические примитивы слоя.
* **LOD 1 (Секция 2):** Средний уровень детализации.
* **LOD 2 (Секция 3):** Обзорный уровень детализации (наименьшее количество объектов).
Каждый уровень LOD начинается с 16-байтового заголовка, который задает режим работы конечного автомата:
0x00 - 0x03: Сигнатура SQT\x01 (53 51 54 01)

0x04 - 0x07: (Topology Marker: Данное поле является аппаратным переключателем топологии для графического конвейера.
  * `0x00 00 00 00` — Векторная топология (требует чтения `.mlp` файла).
  * `0x01 00 00 00` — Точечная топология (отключает поиск `.mlp`, активирует чтение координат из BBox).
* **Количество уровней слоя POI:** Слой является одноуровневым (только LOD 0). Применяется динамический `Mode Switch` (Flat List `0x00` или Clustered `0x01`). Пустые секции SQT для LOD 1 и LOD 2 не генерируются.

0x08 - 0x0B: LOD Mode Switch (Переключатель режима) (uint32).
  0x00 = Flat List Mode. Оптимизированный режим для слоев с малым количеством объектов. В этом режиме навигационные узлы (Nav Nodes) отсутствуют полностью, а данные лежат сплошным массивом.
  0x01 = Clustered Mode. Используется для слоев с большим объемом геометрии. Включает иерархию Nav Nodes, позволяя парсеру часов использовать Z-Culling (отбрасывание кластеров целиком).
  
0x0C - 0x0F: Count (Счетчик) (uint32).
Если Mode = 0x00, то здесь хранится общее количество объектов (Data Nodes).
Если Mode = 0x01, то здесь хранится количество кластеров (Nav Nodes).

Граница между уровнями детализации определяется исключительно логикой конечного автомата часов (завершение пакетного чтения объектов по счетчикам), никакие терминаторы или выравнивания не применяются. Пустая секция состоит строго из 16 байт заголовка SQT\x01 со значениями Mode = 0 и Count = 0.

Связь LOD с аппаратным Culling'ом:
**Связь LOD с аппаратным Culling'ом:** Для оптимизации памяти часов, компилятор должен распределять объекты по уровням LOD в соответствии с порогами Z-Culling графического процессора. В LOD 1 должны записываться только объекты с порогом видимости `500 м`, в LOD 2 `1000 м`

## 8. ОБХОД ВАЛИДАЦИИ (SYSTEM DUMMIES) И КОНФИГУРАЦИЯ

### 8.1. Пустые слои (System Dummies)
Парсер часов жестко требует наличия как минимум слоя landuse.
Пустые слои взяты из заводских карт пустой области.

### 8.2. Файл конфигурации map.name
Этот файл служит точкой входа для прошивки и определяет параметры центрирования камеры.
* **Формат данных:** Строгий JSON.
* **Обязательная структура:** `{"centerLat": float, "centerLon": float, "mapName": string}`
* **Расчет координат:** Значения `centerLat` и `centerLon` высчитываются как геометрический центр глобального BBox (Bounding Box) всех скомпилированных слоев карты.
* **Критическое требование к парсингу:** Встроенный JSON-парсер часов не переносит лишних whitespaces (пробелов). При использовании Python, сериализацию необходимо выполнять строго с параметром `separators=(',', ':')`, чтобы сжать JSON в единую строку.

## 9. АППАРАТНЫЙ РЕНДЕРИНГ И ТАБЛИЦА СТИЛЕЙ (LUT)

В часах на платформе ATS3085S визуализация опирается на жестко зашитую в ROM таблицу поиска (Look-Up Table), где цвет и толщина линии/полигона определяются 32-битным полем `Type` (Смещение `0x10` в структуре `Data Node`).

### 9.1. Системные алиасы (System Aliases)
В ходе анализа выявлены следующие аппаратные алиасы рендеринга:
* `8200` (Water Layer): Системный ID для заливки полигонов синим цветом. Любые водные объекты (реки, озера, водохранилища) должны быть скомпилированы с этим ID для корректного отображения.
* `5111` - `5112` (Roads Layer): Отрисовка широкой оранжевой линией (Motorway/Trunk).
* `5113` - `5114` (Roads Layer): Отрисовка желтой линией (Primary/Secondary).
* `5124` и выше (Roads Layer): Отрисовка базовой серой линией (Local/Pedestrian).

### 9.2. Аппаратный Z-Culling (LOD)
Прошивка динамически скрывает геометрию в зависимости от масштаба GPS-камеры. Компилятор обязан распределять объекты по блокам в файле `.idx` (SQT-индекс) на основе порогов видимости:
* **LOD 2 (Смещение 0x0E в YZL):** Объекты базовой маршрутизации (Motorways, Water, Крупный Landuse). Порог видимости `>= 1000`.
* **LOD 1 (Плоский список SQT):** Вторичная геометрия. Порог видимости `500`.
* **LOD 0:** Вся геометрия (Тропинки, тротуары). Порог видимости `< 500`.
