# Техническая спецификация формата оффлайн-карт смарт-часов DT G1

**Версия:** 2.5 (Кластерная архитектура)  
**Статус:** Полностью подтверждено реверс-инжинирингом  
**Язык реализации парсеров/компиляторов:** Python 3

---

## 1. Глобальная архитектура картографического пакета

Карта для носимого устройства DT G1 представляет собой папку, содержащую бинарные пространственные слои и один текстовый конфигурационный файл метаданных. 

Каждый бинарный файл картографического слоя строго обязан начинаться с глобального заголовочного блока **YZL** фиксированной длины (32 байта).

### 1.1. Номенклатура слоев и файлов
* **Дорожная сеть (Roads):** `roads.idx`, `roads.mlp`, `roads.db` (Геометрия: Линии / Мультилинии).
* **Землепользование (Landuse):** `landuse.idx`, `landuse.mlp`, `landuse.db` (Геометрия: Полигоны / Мультиполигоны).
* **Гидрография (Water):** `water.idx`, `water.mlp`, `water.db` (Геометрия: Полигоны / Мультиполигоны).
* **Инфраструктура (POI):** `pois.idx`, `pois.db` (Геометрия: Точки. Файл геометрии `.mlp` отсутствует).
* **Метаданные (Meta):** `map.name` (Текстовый JSON, заголовок YZL отсутствует).

---

## 2. Глобальный заголовок YZL (32 байта)

Унифицированный префикс для всех бинарных контейнеров карты.

| Смещение (Hex) | Размер (Байт) | Тип данных | Описание |
| :--- | :--- | :--- | :--- |
| `0x00` | 4 | char[4] | Магическая сигнатура: `YZL\x00` |
| `0x04` | 4 | UInt32 LE | Полный физический размер файла в байтах от начала до конца |
| `0x08` | 24 | bytes | Служебный нулевой паддинг (`\x00`), зарезервирован для выравнивания |

---

## 3. Пространственный индекс (.idx)

Файл индекса организует пространственный поиск объектов без использования тяжелой рекурсии. Данные выстроены в линейный связанный список информационных блоков (кластеров), распределенных по уровням детализации.

### 3.1. Структура LOD-уровней (Levels of Detail)
Файл `.idx` жестко разделен на **3 обязательных LOD-уровня**, соответствующих масштабам отображения (Зум-уровням):
* **LOD 0 (Детальный):** Отрисовка при максимальном приближении (городские улицы, мелкие здания).
* **LOD 1 (Средний):** Отрисовка на средних масштабах (основные шоссе, крупные кварталы).
* **LOD 2 (Обзорный):** Отрисовка при полном отдалении (границы районов, трассы общего пользования).

Каждый LOD-уровень в файле инициируется заголовком `SQT` (8 байт), содержит последовательность блоков данных и **строго завершается терминатором из 8 нулевых байт**. Если LOD-уровень пуст, за заголовком сразу следует терминатор.

#### Заголовок SQT (8 байт):
* `0x00` (4 байта): char[4] — Сигнатура `SQT\x01`
* `0x04` (4 байта): UInt32 LE — Параметр инициализации (всегда `01 00 00 00`)

### 3.2. Архитектура Кластера (Cluster Block)
Для минимизации операций чтения, объекты группируются в плоские кластеры (обычно по 10–20 объектов). Каждый рабочий кластер имеет строго фиксированную трехкомпонентную структуру:

`[ Узел перехода (28 байт) ] -> [ Заголовок кластера (28 байт) ] -> [ Узлы данных (Data Nodes) (N * 28 байт) ]`

#### Компонент 1: Узел перехода (Navigation Node) — 28 байт
Служит для аппаратного пропуска (пролистывания) всего кластера, если его географические границы не попадают на текущий экран часов. Использует структуру `<IIIffff`:

| Смещение | Тип данных | Описание |
| :--- | :--- | :--- |
| `0x00` | UInt32 LE | `v1` (Копируется из первого узла данных текущего кластера для валидации парсера) |
| `0x04` | UInt32 LE | `v2` (Копируется из первого узла данных текущего кластера) |
| `0x08` | UInt32 LE | **`v3` (Указатель прыжка)**. Абсолютное смещение в байтах от конца YZL-заголовка до начала следующего кластера. |
| `0x0C` | Float32 | MinX (Минимальная долгота) общих границ всего кластера |
| `0x10` | Float32 | MinY (Минимальная широта) общих границ всего кластера |
| `0x14` | Float32 | MaxX (Максимальная долгота) общих границ всего кластера |
| `0x18` | Float32 | MaxY (Максимальная широта) общих границ всего кластера |

*Магическая формула прыжка:* Относительное расстояние пропуска вычисляется как `v3 - (Текущий_абсолютный_оффсет - 32)`. Для плоского списка оно всегда равно `(Количество_узлов_данных * 28) + 28`.

#### Компонент 2: Заголовок кластера (Cluster Header) — 28 байт
Объявляет парсеру о начале итерационного считывания объектов кластера. Использует структуру `<IIffffI`:

| Смещение | Тип данных | Описание |
| :--- | :--- | :--- |
| `0x00` | UInt32 LE | **`v1` = 0** (Критический маркер! Сигнализирует часам, что это заголовок группы, а не дорога) |
| `0x04` | UInt32 LE | **`v2` = N** (Количество элементов в группе, включая этот заголовок. То есть: `Кол-во_объектов + 1`) |
| `0x08` | Float32 | MinX границ кластера |
| `0x0C` | Float32 | MinY границ кластера |
| `0x10` | Float32 | MaxX границ кластера |
| `0x14` | Float32 | MaxY границ кластера |
| `0x18` | UInt32 LE | Code (Внутренний код стиля отображения, берется от первого объекта) |

#### Компонент 3: Узлы данных объектов (Data Nodes) — по 28 байт каждый
Описывают конкретные пространственные объекты. Идут непрерывным массивом длиной `N - 1` штук. Используют структуру `<IIffffI`:

| Смещение | Тип данных | Описание |
| :--- | :--- | :--- |
| `0x00` | UInt32 LE | **`v1`** — Базовое относительное смещение геометрии объекта внутри файла `.mlp` |
| `0x04` | UInt32 LE | **`v2`** — Индекс текстовых атрибутов объекта в базе `.db` |
| `0x08` | Float32 | MinX (Западная граница BBox объекта) |
| `0x0C` | Float32 | MinY (Южная граница BBox объекта) |
| `0x10` | Float32 | MaxX (Восточная граница BBox объекта) |
| `0x14` | Float32 | MaxY (Северная граница BBox объекта) |
| `0x18` | UInt32 LE | Code (Внутренний код классификации стиля: например, `5122` — жилая улица) |

*Правило именования (`v2`):*
* Если объект имеет имя (запись в `.db`), то `v2 = db_index + 1`.
* Если объект безымянный, он обязан ссылаться на пустую запись Record 0 в базе данных, то есть **`v2 = 1`**.

## 4. Файл геометрии (.mlp)

Хранит физические массивы точек (координат) для линий и полигонов. Все координаты приводятся к целочисленному виду путем умножения на миллион: `int(координата * 1_000_000)`.

### 4.1. Формула перехода из IDX в MLP
Чтобы прочитать геометрию объекта, зная его `v1` из файла индекса, парсер вычисляет точный абсолютный байтовый оффсет в файле `.mlp`:
`AbsOffset_mlp = v1 + 32 (YZL_SIZE) - 8`

### 4.2. Структура записи геометрии (Geometry Record)
Каждая запись состоит из фиксированного заголовка (32 байта) и динамического тела.

#### Заголовок записи (32 байта):
* `0x00` (4 байта): UInt32 BE (!Важно: Big Endian) — Порядковый номер геометрии (Record Number, начиная с 1).
* `0x04` (4 байта): UInt32 LE — Длина тела геометрии в байтах (Content Length).
* `0x08` (4 байта): Int32 LE — MinX (* 1 000 000)
* `0x0C` (4 байта): Int32 LE — MinY (* 1 000 000)
* `0x10` (4 байта): Int32 LE — MaxX (* 1 000 000)
* `0x14` (4 байта): Int32 LE — MaxY (* 1 000 000)
* `0x18` (4 байта): UInt32 LE — `NumParts` (Количество составных частей/колец полигона. Для дорог всегда `1`).
* `0x1C` (4 байта): UInt32 LE — `NumPoints` (Общее количество точек в объекте).

#### Тело записи (Динамическое):
1.  **Массив смещений частей (`Parts`):** Длина = `NumParts * 4` байт (Тип: UInt32 LE). Содержит индексы точек, с которых начинаются составные части геометрии или внутренние кольца (holes) полигонов. Первый элемент всегда равен `0`.
2.  **Массив координат (`Points`):** Длина = `NumPoints * 8` байт (Тип: пары `Int32 LE, Int32 LE`). Последовательный плоский массив целых чисел `[X0, Y0, X1, Y1, X2, Y2...]`.

## 5. Атрибутивная база данных (.db)

Файл атрибутов представляет собой стандартный бинарный контейнер **dBase III (DBF)** с фиксированной длиной записи в **145 байт**.

### 5.1. Поля базы данных (Слои Roads, Landuse, Water)
| Имя поля | Тип DBF | Длина (Байт) | Описание |
| :--- | :--- | :--- | :--- |
| `osm_id` | C (Character) | 12 | Уникальный числовой ID объекта из OpenStreetMap |
| `code` | C (Character) | 4 | Текстовый аналог внутреннего кода стиля (например, `"5122"`) |
| `fclass` | C (Character) | 28 | Классификационный тег OSM (например, `"residential"`, `"water"`) |
| `name` | C (Character) | 100 | Название объекта в кодировке UTF-8, дополненное нулями (`\x00`) |

### 5.2. Важнейшее правило Record 0
Для слоев пространственной геометрии, база данных `.db` **строго обязана содержать в качестве первой записи (Record 0) пустую строку**, полностью забитую нулями (`\x00` * 145). Смещение индекса вычисляется как `db_index = v2 - 1`. Соответственно, все безымянные объекты на карте имеют `v2 = 1`, вычитают единицу и ссылаются на эту пустую запись 0, что предотвращает падение прошивки.

## 6. Метаданные карты (map.name)

Единственный файл конфигурации, написанный в виде открытого текста в формате **JSON**. Он не шифруется и не имеет заголовка `YZL`. Используется операционной системой часов для вывода названия карты в меню выбора и мгновенного сдвига экрана к географическому центру при инициализации.

**Строгие требования к синтаксису:** JSON должен быть упакован в одну строку без использования отступов и символов пробела после двоеточий и запятых.

{"centerLat":53.797876,"centerLon":28.435035,"mapName":"Minsk_Osm"}

## 7. Специфика слоя объектов инфраструктуры (POI)

Слой `pois` разработан по оптимизированной схеме "Point-Only" для экономии оперативной памяти часов:
1.  Файл геометрии `pois.mlp` **полностью отсутствует**.
2.  Физические координаты точек POI хранятся напрямую в индексном файле `pois.idx`.
3.  Для этого BBox узла данных POI искусственно «схлопывается»: параметры `MinX == MaxX` (Долгота) и `MinY == MaxY` (Широта). Часы считывают эту точку напрямую из индекса.
4.  В базе данных `pois.db` **отсутствует пустая запись Record 0**. Индексация прямая: `db_index = v2` (вычитание единицы не производится).

## 8. Алгоритм парсинга (Обратное декодирование в GeoJSON)

Для чтения готовых бинарных файлов карты и преобразования их в стандартный ГИС-формат GeoJSON, парсер должен выполнять следующие шаги:

### Шаг 1: Чтение базы данных (.db)
* Открыть файл `.db`, пропустить YZL (32 байта).
* Распаковать заголовок DBF, считать длину записи (145 байт).
* Прочитать все записи подряд, декодируя строки из UTF-8 (обрезая нули `\x00`), сформировать плоский массив словарей атрибутов `db_records`.

### Шаг 2: Сканирование индекса (.idx)
* Открыть файл `.idx`, считать общий размер файла из YZL заголовка.
* Установить указатель на оффсет `32`. Найти сигнатуру первого LOD-уровня (`SQT\x01`).
* Сдвинуть указатель на `+8` байт (размер SQT заголовка).
* Запустить цикл чтения блоков по 28 байт до тех пор, пока не встретится терминатор (8 байт нулей) или сигнатура следующего уровня `SQT`.
* **Логика разбора узла (28 байт):**
    * Распаковать `v1` и `v2` (первые 8 байт).
    * Если `v1 == 0` — это *Заголовок кластера*. Считать `v2` как количество последующих объектов `Count`, запомнить текущий `Code`. Пропустить этот узел.
    * Если `v1 > 0` (или `v1 == 0` для слоя POI, но `v2` указывает на валидный ID) — это *Узел данных*. Сохранить его `v1`, `v2`, `BBox` и `Code` в массив объектов для экспорта.
    * Если у узла `v1 == 0` и `v2 == 0` (или `v3 > 0` на третьей позиции) — это *Узел перехода*. Пропустить его, так как при полном последовательном чтении прыжки не требуются.

### Шаг 3: Извлечение геометрии из MLP и сборка объектов
* Для каждого валидного сохраненного узла данных:
    * **Связь с DB:** Найти атрибуты. Если слой не POI, `idx = v2 - 1`. Если `idx == 0` или не существует — свойства пустые. Если слой POI — `idx = v2`.
    * **Связь с MLP (если не POI):** Вычислить смещение: `Offset = v1 + 24`. Перейти по этому адресу в файле `.mlp`.
    * Распаковать заголовок геометрии (32 байта). Считать `NumParts` и `NumPoints`.
    * Считать массив `Parts` и массив `Points`. Разделить координаты на `1_000_000.0`.
    * Собрать координаты в формат GeoJSON (`LineString` для дорог, `Polygon` для landuse/water).
    * Для POI — сформировать геометрию `Point` напрямую из координат BBox узла индекса.
* Записать итоговый массив в `.geojson` файл.

## 9. Алгоритм компиляции карт (Сборка из OSM XML в бинарники часов)

Процесс генерации карты из исходных данных OpenStreetMap происходит в обратном порядке и требует строгого контроля за математическими указателями.

### Шаг 1: Фильтрация и кэширование исходного OSM
* Прочитать файл `map.osm`. Собрать в кэш оперативки все элементы `<node>` в виде словаря `{ node_id: (lon, lat) }`.
* Отфильтровать элементы `<way>` по целевому слою (например, для дорог ищем тег `highway`, для воды — `waterway` или `natural=water`).
* Собрать геометрию линий/полигонов, подтягивая координаты точек из кэша узлов.

### Шаг 2: Компиляция геометрии и создание метаданных (.mlp + roads_meta.json)
* Открыть бинарный файл `.mlp` на запись. Записать пустой заголовок YZL (32 байта).
* Инициализировать счетчик `AbsOffset = 32` и `RecordNumber = 1`.
* Для каждого валидного географического объекта:
    * Вычислить его индивидуальный ограничивающий прямоугольник BBox (`MinX, MinY, MaxX, MaxY`).
    * Рассчитать центроид объекта (географический центр) для последующей сортировки.
    * Записать 32-байтный заголовок геометрии (переведя координаты в целые числа `* 1_000_000`, а `RecordNumber` упаковать в Big Endian).
    * Записать массивы `Parts` и `Points`.
    * Вычислить относительный указатель для индексного файла: **`v1 = AbsOffset - 24`**.
    * Сохранить `v1`, оригинальные координаты BBox, центроид, теги и имя во временный JSON-файл метаданных проекта (`roads_meta.json`).
    * Увеличить `AbsOffset` на полную длину записанного бинарного блока. Нарастить `RecordNumber` на 1.
* Обновить поле длины файла в заголовке YZL в самом начале файла `.mlp`.

### Шаг 3: Группировка в кластеры и генерация пространственного индекса (.idx)
* Загрузить временный файл `roads_meta.json`.
* Отсортировать все объекты по географическому положению (например, по долготе или широте центроида), чтобы близкие объекты оказались рядом.
* Нарезать упорядоченный список объектов на чанки (группы) строго (возможно, в заводских картах размеры различные) по **15 объектов** в каждой (последний чанк может быть меньше).
* Открыть файл `.idx` на запись. Записать заголовок YZL (32 байта).
* Записать сигнатуру первого зум-уровня: `b'SQT\x01\x01\x00\x00\x00'`.
* Запустить цикл сборки бинарных кластеров:
    * Для текущего чанка из 15 дорог вычислить **Общий географический BBox**, охватывающий все 15 элементов.
    * **Запись Узла перехода:** Рассчитать `v3` прыжка по формуле: `branch_v3 = (Количество_объектов_в_чанке + 1) * 28 + 8`. Упаковать структуру `<IIIffff`, где первые две переменные `v1` и `v2` дублируют параметры первого реального объекта группы (обман парсера), на третью позицию положить `branch_v3`, а далее — Общий BBox.
    * **Запись Заголовка кластера:** Упаковать структуру `<IIffffI`. Задать `v1 = 0`, `v2 = Количество_объектов + 1`, далее — Общий BBox, в конце — код стиля первого объекта.
    * **Запись Узлов данных:** Для каждого из 15 объектов упаковать его индивидуальные параметры в структуру `<IIffffI`: записать его личный `v1` (полученный на Шаге 2), его индекс `v2` в будущей базе данных, его личный Float-BBox и код стиля.
* После записи всех кластеров дописать терминатор уровня: `b'\x00' * 8`.
* Дописать пустые болванки для уровней LOD 1 и LOD 2 (заголовок SQT + 8 байт нулей для каждого).
* Обновить поле длины файла в главном заголовке YZL в самом начале файла `.idx`.

### Шаг 4: Компиляция базы данных атрибутов (.db)
* Сформировать список только тех объектов, которые имеют название (тег `name` или `int_name`).
* При формировании индекса на Шаге 3, присвоить этим объектам последовательные ID, начиная с `2`: (`v2 = 2, 3, 4...`). Всем безымянным объектам жестко прописать `v2 = 1`.
