# ТЕХНИЧЕСКАЯ СПЕЦИФИКАЦИЯ ФОРМАТА КАРТ DT G1 (Реверс-инжиниринг)

**Версия:** 4.0 (C-Union Node / Mode Switch)
**Область применения:** Компиляторы/декомпиляторы ГИС-данных для носимых устройств на платформе ATS3085S (DT NO.1 G1)

---

## 1. ГЛОБАЛЬНЫЙ ЗАГЛОВОК СЛОЯ (YZL HEADER)

Каждый бинарный файл картографического слоя (`.idx`, `.mlp`, `.db`) обязан начинаться с глобального системного заголовка фиксированной длины **32 байта**. Заголовок используется загрузчиком прошивки для маппинга памяти и проверки целостности по алгоритму MD5.

### 1.1. Побайтовая структура заголовка YZL

| Смещение | Размер | Тип данных | Описание поля | Значение / Формат |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 3 | `char[3]` | **Магическая сигнатура (Magic)** | Строго `b'YZL'` (`59 5A 4C`) |
| `0x03` | 1 | `uint8` | **Расширение магии файла** | Для `.mlp` и `.db` = `0x00`. Для `.idx` переменное (`0x08`, `0x10`, `0x0C` и др.) |
| `0x04` | 4 | `uint32` | **Размер полезной нагрузки (Payload Size)** | В байтах (Little-Endian). Формула: `Размер файла - 32` |
| `0x08` | 4 | `uint32` | **Тип загрузки в RAM** | Для `.mlp`/`.db`/`pois.idx` = `0x04000000` (LE: `b'\x00\x00\x00\x04'`). Для `.idx` = `0x04000002` (LE: `b'\x02\x00\x00\x04'`) |
| `0x0C` | 4 | `uint32` | **Размер секции LOD 2** | В байтах (Big-Endian). Для `fseek` с конца файла (быстрый расчет указателя). Для `.mlp` и `.db` = `0x00000000` |
| `0x10` | 16 | `byte[16]`| **Контрольная сумма MD5** | Вычисляется аппаратно от тела полезной нагрузки (от `0x20` до EOF) |

> **Исключение для слоя POI (`pois.idx`):**
> * **Смещение `0x03` (Расширение магии):** Значение строго `0x00`.
> * **Смещение `0x08` (Тип загрузки в RAM):** Принимает значение `0x04000000` (Little-Endian: `b'\x00\x00\x00\x04'`), идентично заголовкам `.mlp` и `.db`.

## 2. СТРУКТУРА ФАЙЛА ГЕОМЕТРИИ (.MLP)

Файл `.mlp` содержит сырые упорядоченные координаты вершин линейных и полигональных объектов (унифицированное хранилище полилиний/полигонов). Координаты представлены в целочисленном формате фиксированной точности.

### 2.1. Локальный заголовок геометрии (Geometry Record Header)
Сразу после 32 байт глобального заголовка YZL начинается массив записей геометрии. Каждая запись предваряется собственным 8-байтовым мини-заголовком.

| Смещение | Размер | Тип данных | Эндианность | Описание поля |
| :--- | :--- | :--- | :--- | :--- |
| `0x00` | 4 | `uint32` | **Big-Endian** (`>I`) | Порядковый номер геометрической записи (начиная с 1) |
| `0x04` | 4 | `uint32` | **Little-Endian** (`<I`) | Длина тела геометрической записи в байтах (Content Length) |

### 2.2. Тело геометрической записи
Размер тела записи в байтах строго равен значению поля `Content Length`.

| Смещение | Размер | Тип данных | Описание поля / Специфика |
| :--- | :--- | :--- | :--- |
| `0x00` | 16 | `int32[4]` | `bbox_int` = `[minx, miny, maxx, maxy]` |
| `0x10` | 4 | `int32` | `num_parts` — суммарное количество сегментов/колец в объекте |
| `0x14` | 4 | `int32` | `num_points` — суммарное количество точек (вершин) в объекте |
| `0x18` | `num_parts * 4` | `uint32[]` | Массив `parts`. Индексы точек (смещения), с которых начинается каждый сегмент (от 0). *Не длины контуров, а индексы.* |
| `0x18 + (num_parts * 4)` | `num_points * 8` | `int32[2][]` | Массив `points` (пары `[X, Y]`). Перевод в Float: `Координата = Значение / 1000000.0` |

### 2.3. Топология полигонов (Мультиполигоны)
Аппаратный триангулятор поддерживает структуру сложных полигонов (например, озер с островами), аналогичную формату ESRI Shapefile:

* Все точки всех колец (как внешних контуров, так и внутренних "дырок") сплющиваются в единый массив `points`.
* Поле `num_parts` указывает общее количество колец в мультиполигоне.
* Массив `parts` содержит индексы начала каждого кольца (например, `[0, 41]`).
* Кольца обязаны быть замкнутыми (первая и последняя координата контура совпадают).
* Одиночные замкнутые полигоны всегда классифицируются как Outer и закручены по часовой стрелке.

**Winding Rules (Правило обхода):**
* **Outer (Внешние контуры):** Строго **По часовой стрелке (Clockwise, CW)**.
* **Inner (Внутренние дырки):** Строго **Против часовой стрелки (Counter-Clockwise, CCW)**.

## 3. СТРУКТУРА ПРОСТРАНСТВЕННОГО ИНДЕКСА (.IDX)

Файл `.idx` организует данные по уровням детализации (LOD) и кластеризует их для быстрого отсечения невидимой геометрии (BBox Culling).

### 3.1. Архитектура Flat List и аппаратный автомат состояний
Внутри LOD объекты упакованы в плоские группы (кластеры) фиксированного размера (максимум по 14 объектов данных). Движок использует унифицированный 28-байтовый фрейм как для Навигационных узлов (Nav Node), так и для Узлов данных (Data Node).

Фундаментальное правило: последние 8 байт любого узла (смещение `+20` и `+24`) всегда являются указателями `v1` и `v2`. Это позволяет аппаратному парсеру перемещаться по графу памяти, не анализируя тип узла.

### 3.2. Спецификация типов узлов (C-Union Pattern)

```c
struct UnifiedNode {
    union {
        struct { float xmin, ymin, xmax, ymax; uint32_t type; } data; // 20 bytes
        struct { uint32_t v3_jump; float xmin, ymin, xmax, ymax; } nav;  // 20 bytes
    } payload;
    uint32_t v1;  // offset 20
    uint32_t v2;  // offset 24
};
```

#### 1. Data Node (Узел данных)
Содержит сам картографический примитив. Распаковка (Python): `<ffffIII`.

| Смещение | Размер | Тип | Описание |
| :--- | :--- | :--- | :--- |
| `0x00 - 0x0F` | 16 | `float[4]` | BBox (xmin, ymin, xmax, ymax) |
| `0x10 - 0x13` | 4 | `uint32` | **Type** (Код класса объекта OSM, например, `5114` — secondary road) |
| `0x14 - 0x17` | 4 | `uint32` | **v1** (Указатель на Payload в `.mlp`). Должен пропускать 8 байт заголовка геометрии |
| `0x18 - 0x1B` | 4 | `uint32` | **v2** (Индекс в `.db`). `1` — пустая запись (без имени), `>=2` — уникальные имена |

> **Аномалия слоя POI (`pois.idx`):**
> * Файл `pois.mlp` не существует.
> * **Инъекция центроида:** Замкнутые полигоны (например, здания, магазины) динамически преобразуются в точки во время компиляции путем вычисления их математического центроида.
> * **Смещение `0x00 - 0x0F` (Инъекция точки):** 32-битные Float координаты записываются напрямую в BBox. Требуется строгое дублирование: `minX == maxX` и `minY == maxY`.
> * **Смещение `0x14 - 0x17` (v1):** Игнорируется графическим парсером при маркере топологии `0x00000001` (`b'\x01\x00\x00\x00'`). В текущей реализации `v1` принудительно устанавливается в `0`.
> * **Сжатие R-Tree:** Большие массивы POI теперь также используют иерархическое сжатие R-Tree (STR), подобно стандартным векторным слоям.

#### 2. Nav Node (Navigation Node / Macro Node)
Открывает геометрию (Mode 0x00) или ветку иерархического R-дерева (Mode > 0x01).
Формат распаковки (Python): `<IffffII`.

| Смещение | Размер | Тип | Описание |
| :--- | :--- | :--- | :--- |
| `0x00 - 0x03` | 4 | `uint32` | `v3_jump` (Прыжок Early Exit). Размер всего дочернего поддерева в байтах + 8 байт компенсации префетча. |
| `0x04 - 0x13` | 16 | `float[4]` | BBox кластера (охватывает все вложенные дочерние BBox) |
| `0x14 - 0x17` | 4 | `uint32` | `v1` (Глубина дерева). `0` = потомками являются `Data Node`. `>0` = потомками являются макро-узлы (`Nav Node` с уровнем `v1 - 1`). |
| `0x18 - 0x1B` | 4 | `uint32` | `v2` (Количество дочерних узлов непосредственно внутри текущего кластера). |

> **Внимание:** Поле `v3_jump` требует обязательной аппаратной компенсации префетча (`+8` байт к длине прыжка).

## 4. СТРУКТУРА БАЗЫ ДАННЫХ АТРИБУТОВ (.DB)

Файл `.db` хранит текстовые наименования (теги `name`). Формат представляет собой стандартную СУБД **dBase III (DBF)**, инкапсулированную в контейнер YZL.

### 4.1. Спецификация заголовка DBF (Размер: 161 байт)
Начинается со смещения `0x20` (сразу после заголовка YZL).
* **Магический байт dBase III:** `0x03` (Смещение `0x20`).
* **Количество записей:** 4 байта (LE) на смещении `0x24`. `(Именованные объекты + 1)`.
* **Размер заголовка БД:** Строго `161` (`0xA1 0x00`) на смещении `0x28`.
* **Размер записи:** Строго `145` (`0x91 0x00`) на смещении `0x2A`.

### 4.2. Маппинг полей записи
Длина описания каждого поля — 32 байта. Терминатор описания полей — `0x0D`. 
1. `osm_id` (Тип `C`, 12 байт).
2. `code` (Тип `C`, 4 байта).
3. `fclass` (Тип `C`, 28 байт).
4. `name` (Тип `C`, 100 байт).

### 4.3. Важность записи №0
Первая физическая запись данных в `.db` (145 байт) **строго обязана быть заполнена нулями** (`\x00`).
* На нее ссылаются безымянные объекты карты (указатель `v2 = 1`).
* Именованные записи упаковываются следом (`v2 = 2`, `v2 = 3` и т.д.).
* Каждая запись начинается с байта `0x20` (индикатор валидности dBase).

> **Пропуск создания .db:**
> Если слой не содержит именованных объектов (и не является слоем POI), создание файла `.db` полностью пропускается, и все объекты получают `v2 = 0`.

> **Исключение для слоя POI:**
> В `pois.db` нулевая заглушка отсутствует. Первая запись данных начинается сразу после терминатора `0x0D`. Применяется 1-based indexing: `v2 = 1` ссылается на первую физическую запись. Безымянные POI получают `v2 = 0`.

## 5. АЛГОРИТМЫ ОПЕРАЦИЙ (ПСЕВДОКОД)

### 5.1. Алгоритм компиляции пространственного индекса (IDX)

**ВХОД:** Список объектов с вычисленными `v1` (из MLP), `v2` (из DB), BBox и Code.
**ВЫХОД:** Бинарный файл картографического слоя `.idx`.

1. Инициализировать пустой байтовый буфер `idx_body`.
2. Применить алгоритм массовой загрузки Sort-Tile-Recursive (STR) для аппаратного Z-Culling:
   * Отсортировать объекты по оси X (долгота центроида).
   * Вычислить математические границы срезов (чанки до 14 элементов).
   * Нарезать вертикальные срезы и отсортировать их по оси Y (широта центроида).
   * Упаковать в кластеры C-Union (по 14 элементов) для формирования иерархических макро-узлов R-Tree (Nav Nodes).
3. Для каждого узла (рекурсивно):
   * Вычислить ограничивающий прямоугольник (Enveloping BBox) для всех потомков.
   * Вычислить аппаратный прыжок `v3_jump` = размер всего дерева под этим узлом + 8 байт компенсации префетча.
4. Скомпилировать секции LOD 0, LOD 1 и LOD 2.
   * Добавить 16-байтовый заголовок: `b'SQT\x01\x01\x00\x00\x00'` + `pack("<II", depth, root_nodes_count)`.
   * Узлы всегда располагаются последовательно.
   * Если LOD пуст, секция состоит ровно из 16 байт: `[SQT\x01] [01 00 00 00] [00 00 00 00] [00 00 00 00]`.
5. Вычислить `lod2_size` (точный размер секции LOD 2).
6. Сгенерировать заголовок YZL и добавить `idx_body` в файл `LAYER_NAME.idx`.

### 5.2. Аппаратный алгоритм парсинга конечным автоматом

```python
def parse_node(file, is_nav_node, current_level):
    if not is_nav_node:
        # Чтение Data Node
        data_bytes = file.read(28)
        xmin, ymin, xmax, ymax, obj_type, v1, v2 = struct.unpack("<ffffIII", data_bytes)
        render_object(xmin, ymin, xmax, ymax, obj_type, v1, v2)
        return

    # Чтение Nav Node
    nav_bytes = file.read(28)
    v3_jump, c_xmin, c_ymin, c_xmax, c_ymax, nav_level, obj_count = struct.unpack("<IffffII", nav_bytes)

    if not is_in_screen(c_xmin, c_ymin, c_xmax, c_ymax):
        # Culling: Прыжок к следующему Nav Node
        # v3_jump УЖЕ включает +8 байт компенсации префетча аппаратного конвейера!
        file.seek(v3_jump - 8, 1) # Эквивалент SEEK_CUR
        return

    # Кластер видим, рекурсивное чтение вложенных узлов
    for _ in range(obj_count):
        parse_node(file, nav_level > 0, nav_level - 1 if nav_level > 0 else 0)

# 1. Чтение заголовка SQT (16 байт)
magic, res, depth, count = struct.unpack("<IIII", file.read(16))

if count == 0:
    return # Пустой LOD, переход к следующему

for _ in range(count):
    parse_node(file, depth > 0, depth - 1 if depth > 0 else 0)
```

## 6. ВНУТРЕННЯЯ ТАБЛИЦА СТИЛЕЙ (LUT) И АППАРАТНЫЙ Z-CULLING

Поле `code` жестко привязано к внутренней таблице стилей Look-Up Table (LUT), соответствующей стандарту **Geofabrik GIS**. Часы не рендерят все объекты постоянно, применяя **аппаратный Z-Culling**. 

**Жестко закрепленные пороги видимости (Масштаб дисплея):**
* **Масштаб 1000+ м:** Только главные магистрали (`5111`, `5112`, `5113`, `5114`). Полигоны (landuse, water) аппаратно блокируются GPU.
* **Масштаб 500 м:** Второстепенные дороги и съезды (`5115`, `513x`). Разрешается рендеринг водоемов и лесов.
* **Масштаб 100 м:** Улицы местного значения (`512x`).
* **Масштаб 50 м:** Сельскохозяйственные и технические дороги (`514x`).
* **Масштаб 20 м (Макс. зум):** Пешеходные и велосипедные дорожки, ступени (`515x`).

> **Инженерный вывод:** Неизвестные коды или мелкие дороги на крупных масштабах игнорируются. Для принудительного отображения (например, велодорожки `5152` издалека), её `code` должен быть переназначен при компиляции на код с меньшим порогом (например, `5141`).

## 7. МНОГОУРОВНЕВОЕ МАСШТАБИРОВАНИЕ SQT (LOD 0, LOD 1, LOD 2)

Файл `.idx` содержит три последовательных списка пространственного индекса, разделенных сигнатурами `SQT\x01`.
* **LOD 0 (Секция 1):** Уровень максимальной детализации. Охватывает все примитивы.
* **LOD 1 (Секция 2):** Средний уровень детализации.
* **LOD 2 (Секция 3):** Обзорный уровень детализации.

Каждый уровень LOD начинается с 16-байтового заголовка (автомата состояний):

| Смещение | Описание поля | Значение / Формат |
| :--- | :--- | :--- |
| `0x00 - 0x03` | **Сигнатура** | `SQT\x01` (`53 51 54 01`) |
| `0x04 - 0x07` | **Маркер топологии** | Строго `0x00000001` (LE: `b'\x01\x00\x00\x00'`) как для векторного, так и для точечного режимов. |
| `0x08 - 0x0B` | Переключатель режима LOD | `0x00` = Flat List<br>`0x01` = Одноуровневые кластеры<br>`>0x01` = Глубина R-дерева (Например, `0x05` означает 5 уровней вложенности Nav Nodes). |
| `0x0C - 0x0F` | Count | Количество корневых узлов верхнего уровня (внутри текущего SQT-блока). |

Граница между уровнями детализации определяется логикой автомата состояний (завершение пакетного чтения). Пустая секция состоит строго из 16 байт с `Mode = 0` и `Count = 0`. Слой POI является одноуровневым (только LOD 0), но если слой полностью пуст, он все равно сгенерирует 16-байтовый пустой заголовок: `b'SQT\x01\x01\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00\x00'`.

**Связь LOD с Z-Culling:** Объекты распределяются по LOD в соответствии с порогами. Объекты с порогом `500 м` пишутся в LOD 1, а `1000 м` в LOD 2.

## 8. ОБХОД ВАЛИДАЦИИ (SYSTEM DUMMIES) И КОНФИГУРАЦИЯ

### 8.1. Пустые слои (System Dummies)
Парсер часов жестко требует наличия как минимум слоя `landuse`. Для пустых областей используются заводские заглушки (System Dummies).

### 8.2. Файл конфигурации map.name
Служит точкой входа для прошивки и центрирования камеры. Формат — строгий JSON.
* **Структура:** `{"centerLat":float,"centerLon":float,"mapName":"string"}`
* Центр рассчитывается по глобальному BBox всех слоев карты.
* **Критическое требование:** Встроенный JSON-парсер не переносит пробелов (whitespaces). При компиляции применяйте минификацию: `json.dumps(data, separators=(',', ':'))`.

## 9. АППАРАТНЫЙ РЕНДЕРИНГ И ТАБЛИЦА СТИЛЕЙ (LUT)

Визуализация опирается на зашитую в ROM таблицу поиска (Look-Up Table), где цвет и толщина определяются полем `Type` (Смещение `0x10` в `Data Node`).

### 9.1. Системные алиасы
* `8200` (Слой Water): ID для синей заливки (реки, озера, водохранилища).
* `5111` (Слой Roads): Широкая оранжевая линия (Motorway).
* `5112` - `5114` (Слой Roads): Желтая линия (Trunk/Primary/Secondary).
* `>= 5124` (Слой Roads): Базовая серая линия (Local/Pedestrian).

### 9.2. Аппаратный Z-Culling (LOD Mapping)
Компилятор обязан распределять объекты по блокам `.idx` на основе порогов:
* **LOD 2 (Смещение `0x0E` в YZL):** Базовая маршрутизация (Motorways, Water, Крупный Landuse). Порог видимости `>= 1000`.
* **LOD 1 (Плоский список SQT):** Вторичная геометрия. Порог видимости `500`.
* **LOD 0:** Вся геометрия (вкл. тропинки и тротуары). Порог видимости `< 500`.
