# Спецификация формата оффлайн-карт DT G1

**Версия:** 2026-05-12  
**Статус:** Reverse Engineered / Mostly Confirmed  
**Объект исследования:** Бинарный формат оффлайн-карт смарт-часов DT G1

---

# 1. Общая структура карт

Карта представляет собой каталог с набором бинарных файлов.

Каждый файл (кроме `map.name`) начинается с глобального заголовка `YZL`.

## 1.1. Слои карты

| Слой | Файлы | Тип геометрии |
|---|---|---|
| Roads | `roads.idx`, `roads.mlp`, `roads.db` | Линии / MultiLineString |
| Landuse | `landuse.idx`, `landuse.mlp`, `landuse.db` | Полигоны |
| Water | `water.idx`, `water.mlp`, `water.db` | Полигоны |
| POI | `pois.idx`, `pois.db` | Точки |

---

# 2. Глобальный заголовок YZL

Все бинарные файлы начинаются с одинакового заголовка длиной 32 байта.

## 2.1. Структура

| Offset | Размер | Тип | Описание |
|---|---|---|---|
| 0x00 | 4 | char[4] | Сигнатура `YZL\0` |
| 0x04 | 4 | UInt32 LE | Размер / длина |
| 0x08 | 24 | bytes | Служебные данные |

## 2.2. Важно

Полезная нагрузка начинается со смещения:

```text
0x20 (32)
```

---

# 3. Пространственный индекс (*.idx)

Файл `.idx` содержит одно или несколько пространственных деревьев SQT.

---

# 4. Формат дерева SQT

## 4.1. Заголовок дерева
Каждое дерево начинается с сигнатуры `SQT\x01`. 
Размер заголовка дерева: **8 bytes** (а не 36, как предполагалось ранее).

## 4.2. Структура заголовка
| Offset | Размер | Тип | Описание |
|---|---|---|---|
| 0x00 | 4 | char[4] | `SQT\x01` |
| 0x04 | 4 | UInt32 LE | Параметр дерева (например, ID или версия) |

Сразу после этих 8 байт начинаются узлы дерева по 28 байт.

---

# 5. Узлы дерева IDX

После заголовка идут узлы фиксированного размера:

```text
28 bytes
```

Существуют два типа узлов:

- Branch
- Leaf

---

# 6. Структура узла дерева (Union)

Каждый узел занимает фиксированные **28 байт**. Формат узла представляет собой объединение (union), где назначение байтов меняется в зависимости от типа узла: внутренний (Branch) или конечный (Leaf).

## 6.1. Общие поля
Первые 8 байт идентичны для всех узлов:
| Offset | Размер | Тип | Поле |
|---|---|---|---|
| 0x00 | 4 | UInt32 LE | v1 |
| 0x04 | 4 | UInt32 LE | v2 |

## 6.2. Эвристика определения типа узла (Правило 1 000 000)
Тип узла определяется по значению `UInt32` по смещению `0x08`:

- Если `UInt32(0x08) < 1 000 000` — это **Branch** узел.
- Если `UInt32(0x08) >= 1 000 000` — это **Leaf** узел.

*Примечание: в координатах Leaf-узла по смещению 0x08 лежит float-значение долготы (MinX, например ~28.xxx). В бинарном представлении IEEE 754 это число интерпретируется как целое `> 1.1 млрд`, что делает эвристику абсолютно надежной.*

## 6.3. Branch Node (Внутренний узел)
Узлы маршрутизации внутри дерева. 
**Внимание:** В отличие от классических R-деревьев, в формате DT G1 внутренние узлы **МОГУТ содержать реальные картографические объекты** (например, протяженные улицы или крупные мультиполигоны). 
У таких Branch-узлов параметры `v1` (> 0) и `v2` валидны и указывают на геометрию и атрибуты, так же как у Leaf-узлов. У Branch-узла отсутствует собственное поле `code` (срезано сдвинутым BBox), но код объекта восстанавливается из привязанной базы `.db`.

| Offset | Размер | Тип | Поле |
|---|---|---|---|
| 0x08 | 4 | UInt32 LE | v3 (счетчик/индекс маршрутизации) |
| 0x0C | 16 | 4 × Float32 | BBox (MinX, MinY, MaxX, MaxY) |

## 6.4. Leaf Node (Конечный узел)
Узлы, содержащие реальные объекты карты.
| Offset | Размер | Тип | Поле |
|---|---|---|---|
| 0x08 | 16 | 4 × Float32 | BBox (MinX, MinY, MaxX, MaxY) |
| 0x18 | 4 | UInt32 LE | code (внутренний код объекта) |

Значения `v1` и `v2` в Leaf-узлах используются для связи с файлами `.mlp` и `.db` (см. Раздел 9).

# 9. Связь IDX ↔ DB

---

# 9.1. Roads / Landuse / Water

Файлы `.db` содержат только объекты с именами.

При этом:

```text
Record 0 в DB пустой
```

Поэтому связь:

```text
db_index = v2 - 1
```

## Пример

| v2 | DB Record |
|---|---|
| 1 | 0 |
| 2 | 1 |
| 3 | 2 |

---

# 9.2. POI

POI используют другой формат базы. В `pois.db` нулевая запись **не пустая**, она содержит реальный объект.

Однако в официальном компиляторе карт DT G1 присутствует баг смещения (wrap-around bug) при генерации БД для слоя POI:
Значения `v2` в `pois.idx` являются 1-based (от `1` до `N`), но последний элемент дерева (`v2 == N`) всегда записывается в `pois.db` под физическим индексом `0`. 

Следовательно, формула привязки:
if v2 == len(db_records):
    db_index = 0
else:
    db_index = v2

Используется только для:

- roads
- landuse
- water

POI не используют `.mlp`.

# 11. Структура MLP

Файл содержит последовательность записей.

Каждая запись:

```text
8-byte header + geometry body
```

---

# 12. Заголовок записи MLP

| Offset | Размер | Тип | Описание |
|---|---|---|---|
| 0x00 | 4 | UInt32 BE | Record Number |
| 0x04 | 4 | UInt32 LE | Content Length |

---

# 13. Формула перехода IDX → MLP

Абсолютное смещение:

```text
AbsOffset = 32 + v1 - 8
```

Где:

| Значение | Описание |
|---|---|
| 32 | Размер YZL заголовка |
| v1 | Relative offset из IDX |
| -8 | Компенсация заголовка записи MLP |

---

# 14. Тело геометрии MLP

## 14.1. Содержимое

Тело записи содержит:

- Bounding Box
- NumParts
- NumPoints
- Part Offsets
- Координаты

---

## 14.2. Координаты

Координаты хранятся как:

```text
Int32 * 1,000,000
```

Для преобразования:

```python
lon = x / 1_000_000.0
lat = y / 1_000_000.0
```

---

# 15. Геометрия POI

POI не используют `.mlp`.

Координата берётся напрямую из BBox leaf-узла IDX.

Для точки:

```text
MinX == MaxX
MinY == MaxY
```

## Пример

```text
(28.418036, 53.714806) - (28.418036, 53.714806)
```

Это Point:

```json
[28.418036, 53.714806]
```

# 16. Несколько деревьев в IDX

Файл `.idx` содержит несколько SQT-деревьев подряд.

Структура:

```text
Tree0
Tree1
Tree2
...
```

# 17. Padding между деревьями

Между концом последнего узла одного дерева и сигнатурой `SQT\x01` следующего дерева может находиться служебный мусор (padding) произвольной длины (экспериментально подтверждены вставки по 8 и 12 байт).

Новое дерево **НЕ обязано** начинаться сразу после завершения 28-байтного блока предыдущего узла. Мусор может «вклиниваться» на любом байте, ломая жесткое чтение по 28 байт.
---

# 18. Правильный алгоритм парсинга IDX

## 18.1. Нельзя

Нельзя читать `.idx` как непрерывный массив 28-байтных записей.

---

## 18.2. Нужно

Перед чтением каждого узла необходимо искать сигнатуру:

```text
SQT\x01
```

---

## 18.3. Алгоритм чтения IDX

1. Прочитать глобальный YZL header (32 байта).
2. Peek вперёд на 4 байта (без сдвига указателя).
3. Если найдена сигнатура `SQT\x01`:
   - прочитать 8 байт (заголовок дерева).
   - начать новое дерево.
4. Иначе прочитать 28 байт (узел дерева):
   - Распаковать `v1` и `v2` из первых 8 байт.
   - Распаковать BBox, предполагая, что это **Leaf** (смещение 0x08).
   - **Эвристика для POI:** Если `MinX == MaxX` и `MinY == MaxY` (и они не равны 0.0), значит это 100% Leaf-узел (точка). Данные верны, извлекаем `code` со смещения 0x18.
   - Если эвристика не сработала (координаты не образуют точку или BBox выглядит как мусор), узел интерпретируется как **Branch**. Значение по смещению 0x08 читается как `UInt32 v3`, а BBox читается со смещения 0x0C.

# 27. Алгоритм экспорта в GeoJSON

Этот раздел описывает практический порядок преобразования бинарной карты DT G1 в GeoJSON.

## 27.1. Общая цель

Экспорт в GeoJSON должен:

- сохранять геометрию объектов;
- не терять безымянные объекты;
- подставлять атрибуты только по правильной связке;
- различать слои `roads`, `landuse`, `water`, `pois`;
- быть пригодным для визуальной проверки в `geojson.io`.

## 27.2. Основной принцип

Экспорт строится по схеме:

- для `roads`, `landuse`, `water`:
  - геометрия берётся из `*.mlp`;
  - атрибуты берутся из `*.db`;
  - связь между ними идёт через `*.idx`.
- для `pois`:
  - геометрия берётся напрямую из `*.idx`;
  - атрибуты берутся из `*.db`;
  - `*.mlp` отсутствует.

## 27.3. Порядок обработки слоёв

Рекомендуемый порядок:

1. Прочитать `map.name`.
2. Для каждого слоя прочитать `*.idx`.
3. Для `roads`, `landuse`, `water` прочитать `*.mlp`.
4. Прочитать `*.db`, если файл существует.
5. Построить набор GeoJSON features.
6. Сохранить итоговый `FeatureCollection`.

## 27.4. Разбор IDX

Файл `*.idx` нужно обрабатывать как набор SQT-деревьев подряд.

### Шаги:

1. Прочитать YZL header (32 байта).
2. Начать цикл сканирования файла:
   - Найти позицию ближайшей сигнатуры `SQT\x01`. Если не найдено — конец файла.
   - Пропустить мусор (padding), если текущая позиция меньше позиции `SQT\x01`.
3. Прочитать 8-байтный заголовок дерева (сигнатура + параметр).
4. Начать чтение узлов блоками по 28 байт:
   - **Критическая проверка:** Перед парсингом узла проверить, где находится следующая сигнатура `SQT\x01`. Если расстояние до нее **меньше 28 байт**, значит текущий блок — это padding. Прервать чтение узлов текущего дерева и перейти к шагу 2.
   - Распаковать `UInt32` по смещению 0x08.
   - Если значение `< 1 000 000`, это Branch узел. 
   - Иначе это Leaf узел. 
   - **Важно для экспорта:** - Для слоя `pois` экспортируются **только** Leaf узлы, у которых BBox схлопнут в точку.
     - Для слоев `roads`, `landuse` и `water` экспортируются **и Leaf, и Branch узлы**, если их поле `v1 > 0` (то есть существует указатель на геометрию).

### Для узлов:

- для `roads`, `landuse`, `water` leaf-узел содержит:
  - `v1` — ссылка на геометрию в `*.mlp`;
  - `v2` — ссылка на запись в `*.db`;
  - `code` — внутренний код;
  - `BBox` — границы объекта.
- для `pois` leaf-узел содержит:
  - `BBox` как точку, если `MinX == MaxX` и `MinY == MaxY`;
  - координаты точки берутся из bbox;
  - `v2` указывает на запись в `*.db`.

## 27.5. Разбор MLP

Для слоёв `roads`, `landuse`, `water`:

1. Найти запись геометрии по `v1` из leaf-узла `idx`.
2. Перейти в `*.mlp` по вычисленному смещению.
3. Прочитать заголовок записи.
4. Прочитать тело геометрии.
5. Построить массив координат.
6. Учитывать `NumParts` и `Parts Array`.

### Геометрические типы:

- `roads` → `LineString` или `MultiLineString`
- `landuse` → `Polygon` или `MultiPolygon`
- `water` → `Polygon` или `MultiPolygon`

## 27.6. Разбор DB

Файл `*.db` используется только для атрибутов.

### Важные правила:

- `db` содержит только объекты с атрибутами/именами;
- безымянные объекты могут отсутствовать в `db`;
- для `roads`, `landuse`, `water` первая запись в `db` является пустой служебной записью;
- для `pois` первая запись в `db` уже содержит реальный объект;
- поэтому индекс записи в `db` считается по-разному:
  - `roads`, `landuse`, `water`: `db_index = v2 - 1`
  - `pois`: `db_index = v2`

## 27.7. Построение GeoJSON Feature

Для каждого объекта создаётся `Feature` со следующей структурой:

```json
{
  "type": "Feature",
  "geometry": { ... },
  "properties": {
    "osm_id": "...",
    "code": "...",
    "fclass": "...",
    "name": "..."
  }
}
```

### Если атрибуты отсутствуют

Если подходящая запись в `db` не найдена, объект всё равно экспортируется, но свойства остаются пустыми:

```json
{
  "osm_id": "",
  "code": "",
  "fclass": "",
  "name": ""
}
```

Это лучше, чем подставить чужое имя.

## 27.8. Особенности слоя POI

Для `pois`:

- файл `pois.mlp` отсутствует;
- геометрия хранится в `pois.idx`;
- POI экспортируются как `Point`;
- координаты берутся из схлопнутого bbox leaf-узла;
- индекс в `db` не сдвигается на `-1`.

## 27.9. Рекомендуемый порядок сопоставления

Для `roads`, `landuse`, `water`:

1. leaf-узел `idx` даёт `v1` и `v2`;
2. по `v1` читается геометрия из `mlp`;
3. по `v2 - 1` читаются атрибуты из `db`;
4. объект добавляется в GeoJSON.

Для `pois`:

1. leaf-узел `idx` даёт координату точки;
2. по `v2` читаются атрибуты из `db`;
3. объект добавляется в GeoJSON как `Point`.

## 27.10. Практические рекомендации

- Не пытаться строить `db`-связь по номеру геометрии `mlp`.
- Не использовать bbox-матчинг как основной способ привязки.
- Не удалять объекты без `name`.
- Не считать отсутствие строки в `db` ошибкой экспорта.
- Сохранять debug-поля при разработке, чтобы видеть `v1`, `v2`, `record_number`, `db_index` и факт наличия записи.

# 28. Краткая итоговая модель экспорта

```text
roads / landuse / water:
    idx leaf.v1 -> mlp geometry
    idx leaf.v2 -> db record (v2 - 1)

pois:
    idx leaf bbox -> point geometry
    idx leaf.v2 -> db record (v2)
```
